# Plan: NGNE-15 — Build the two-level platformer on the current engine

_Round 3 — approved by Codex in round 4 (see `NGNE-15-platformer-review-log.md`)_

Jira: [NGNE-15](https://thatwebdevdude.atlassian.net/browse/NGNE-15) (Task, High, To Do, epic NGNE-17, execution order 05).
Blocked by NGNE-19 (Done). Blocks NGNE-7, NGNE-9, NGNE-10, NGNE-27.

## Goal

Ship `examples/platformer/`: a two-level side-scrolling platformer that is the second real consumer of NGNE's public API, completable in a browser on the current object-column ECS and WebGL 2 renderer. Movement, tile collision, camera follow, checkpoints, death/re-entry, level exits and pause/resume are all game-owned and built only from `ngne` package exports. Every point of authoring friction is recorded as evidence for NGNE-7 (transitions), NGNE-9 (input), NGNE-10 (audio), NGNE-23 (SoA/WebGPU) and NGNE-16 (stable API). Starfall keeps running and every existing check stays green. Done state is engine-independent: no SoA/WebGPU work here (that is NGNE-27).

## Engine facts the design rests on (verified in `src/`)

- `SceneDefinition<S,C>.setup(scene)` is synchronous; bindings (`resource`, `random`, `system`, `render`, `resetInterpolation`, `state`, `defer`) are fixed after setup. Runtime component add/remove is unsupported; composition is fixed at spawn.
- Scene transitions need a **prepared candidate**: `game.prepare(def, { key })` is async and host-side; systems can only `ctx.scenes.set/push/pop(candidate)` synchronously. Candidates are single-use, belong to one Game, and **unused candidates are invalidated by `stop()`** (contract). Starfall hands pre-prepared candidates to scenes through option callbacks; the platformer uses the same shape and records the bookkeeping as NGNE-7 friction.
- Tick commit order: scene updates → world commit → events → freeze → **state commands → stack commands (FIFO)**. A state command dispatched in the same tick as `scenes.set(candidate)` is visible to the replacement's setup. A failed mount keeps the old stack, discards later stack commands for that boundary, and is reported through `diagnostic`; **state already committed is not rolled back**.
- Two `pop()` requests at one boundary remove two scenes. Only scenes may issue stack commands in this example (see D2).
- Committed game state is plain data only, `DeepReadonly`, dispatched only from a system update of the owning scene. Re-entered scenes rebuild from committed facts; entities never move between worlds.
- Camera: `camera.x/y` is the **world coordinate of the screen's top-left** (`Frame.add` subtracts it; the shader maps 0..width left→right, 0..height top→bottom). The engine calls `beginTick()` before ordinary systems and no-argument `cut()` after mount commit; **no-argument `cut()` copies current to previous without moving the camera, while `cut(x, y)` sets both** — so setup must position the camera itself. Starfall never moves the camera; the platformer is the first scrolling consumer.
- Host-visible facts: `game.state` (committed snapshot) and `game.scenes` (frozen summaries with unique instance `id`, definition id and the **authored mount `key`**) are public. The host can therefore recognise a newly mounted instance and read the level/attempt it was mounted with from its key, without any scene-side reporting. `game.state` may already be ahead of that instance (a death committed in a later catch-up tick of the same frame), so it is not the source for the owner's identity.
- `BrowserGame` frame order: `loop.advance` runs 0..5 ticks (each `tick` then `audio.flush`), then `frame.reset` + `game.render` + `renderer.render`, then `afterFrame(stats)`, then the next `requestAnimationFrame`. Promise continuations (asset-free `prepare()` results) run after the callback returns, so a candidate requested in `afterFrame` is ready **before the next frame's first tick**.
- Interpolation: authors own previous/current poses and register `scene.resetInterpolation`. Suspended and just-uncovered scenes render at alpha 1 until their next update; stored poses are never rewritten (NGNE-6).
- Input: `InputSnapshot` with `held/pressed/released` key codes, `axes[0..3]`, pointer. Edges appear on one consuming tick, including ticks where the receiving scene is suspended — **an edge consumed while a scene is suspended is gone**.
- Fixed `dt = 1/60`, 5-tick budget. Headless `Game.tick(input, display)` allows deterministic tests; `game.enumerate()` gives comparable snapshots. Asset-free `prepare()` resolves in microtasks.
- Build: `vite.config.ts` lists page entries explicitly; `tsconfig.json` already includes `examples`; Prettier covers `examples`. CI runs format:check, test, typecheck, build.

### Phase 1 — Playable slice (movement, jump, tile collision, camera) — Jira required work #1

3. Create `examples/platformer/`:
    - `index.html` — canvas 480×270 logical (CSS upscale, `image-rendering: pixelated`), HUD (level, attempt, checkpoint), overlay panel (start / paused / level complete / game complete / error), controls hint, Pause/Resume and Start buttons. Own stylesheet; nothing shared with `demo/`.
    - `levels.ts` — authored data and parser. Symbols: `#` solid, `-` one-way platform, `^` spike, `.` air, `P` start (exactly one), `E` exit (exactly one), `C` checkpoint marker (0..n, ordered left→right by column), `G` patrol spawn. `parseLevel(rows)` validates rectangular rows, known symbols, exactly one `P`/`E`, and that `P`, `C`, `E`, `G` stand on air with a solid or one-way tile directly below; throws with row/column on failure. Output `LevelData { widthTiles, heightTiles, tiles: Uint8Array /* 0 air, 1 solid, 2 one-way, 3 spike */, start, checkpoints: Tile[], exit, patrols: Tile[] }`, frozen. `TILE = 16`. Authored data is code; the mutable per-scene copy is a scene resource.
    - `collision.ts` — pure functions consumed by `game.ts`: `moveX(tiles, box, dx)` / `moveY(tiles, box, dy, previousBottom)` doing axis-separated sweeps in steps ≤ `TILE`, returning contact flags; one-way tiles collide only when moving down and `previousBottom <= tileTop`; spikes are reported as `hazard` contact, not solid; horizontal level bounds act as solid walls; the top is open; `y > (heightTiles + 2) * TILE` is the fall-out line (reported as `fell`). No allocation in the hot path.
    - `game.ts` — `level(options): SceneDefinition<Progress, ProgressCommand>` and `overlay(kind, options)`. Components: `Position {x,y,px,py}`, `Body {vx,vy,w,h,grounded,coyoteTicks,jumpBufferTicks,previousBottom}`, `Actor {kind: 0 player | 1 patrol, facing}`. Resources: `run` (phase, ticks, levelIndex, attempt, checkpoint, deathTimer, pauseRequested, contacts `{fatal, exit, checkpoint}`), `tiles` (Uint8Array copy), `player` (handle). Systems in registration order: (1) host intents + input → intent (latches `pauseRequested`), (2) player physics + collision — **runs only in `playing`**, (3) patrol movement — runs in every phase, (4) contacts: writes facts into `run.contacts` only (checkpoint / exit / hazard / patrol / fall-out), no dispatch, (5) transition authority (see step 10) — the only system that dispatches state commands or issues stack commands, (6) camera follow. `render` draws the visible tile range and entities with `frame.rect`; `resetInterpolation` copies poses.
    - `transitions.ts` — DOM-free host bookkeeping: candidate registry keyed by mounted instance id, intent flags, key derivation, `reconcile(game)` (see step 9). Used by `main.ts` and by tests.
    - `main.ts` — `BrowserGame<Progress, ProgressCommand>` host: DOM wiring, HUD via `afterFrame`, `Enter`/Start to begin, `visibilitychange` → pause intent, `diagnostic` → error panel.
4. Player controller (game-owned): horizontal accel/decel with max speed; gravity with fall speed clamped below `TILE` per tick (no tunnelling); variable-height jump where the cut condition is **`!down(input, jump)`** while rising (not the `released` edge, so a release consumed during pause still cuts on resume); 6-tick coyote time; 6-tick jump buffer. All state in components; no closure-owned gameplay state.
5. Camera follow: horizontal dead-zone, vertical lerp, clamped to level bounds; written each tick after physics. **Setup computes the clamped camera position from the spawn point before returning**, so the engine's post-mount `cut()` publishes a correct first frame.
6. Add `platformer: "examples/platformer/index.html"` to `vite.config.ts` rollup inputs; confirm dev URL `/examples/platformer/` and the production emit.
7. Checkpoint: slice runs in the browser; first-frame and determinism tests pass (Phase 4). Commit `[NGNE-15] Add playable platformer slice`.

### Phase 2 — Two levels, scrolling, progression, death/re-entry, exits, pause — Jira required work #2

8. Committed state (plain data), transition as a pure exported function in `game.ts`:
    ```ts
    interface Progress {
        level: number; // 0, 1 = levels; 2 = game complete
        checkpoint: number; // 0 = level start; k>0 = k-th checkpoint marker (left→right)
        attempt: number; // per-level attempt counter, part of the mount key; reset on exit/restart
        deaths: number; // per-run total, reset on restart
        runs: number; // completed-or-restarted runs, for the HUD
        completed: [boolean, boolean];
    }
    type ProgressCommand =
        | { type: "checkpoint"; checkpoint: number } // only if greater than the current value
        | { type: "died" } // deaths+1, attempt+1
        | { type: "exit" } // completed[level]=true, level+1, checkpoint=0, attempt=0
        | { type: "restart" }; // level 0, checkpoint 0, attempt 0, deaths 0, runs+1
    ```
    Initial: `{ level: 0, checkpoint: 0, attempt: 0, deaths: 0, runs: 0, completed: [false, false] }`.
9. **Candidate ownership (host, `transitions.ts`).** Every candidate has a registry record `{ purpose: "respawn"|"next"|"complete"|"restart"|"pause", ownerId, handle, status: "preparing"|"ready"|"consumed"|"released"|"failed", retries }`. `ownerId` is the **public instance id** of the bottom scene (`game.scenes[0].id`), unique per mount for the Game's lifetime — authored keys are reused across restarts and only seed determinism. The host calls `registry.reconcile(game)` from `afterFrame` (after ticks and render, before the next frame's ticks):
    - If `game.scenes[0].id` differs from the last seen id, a replacement has committed (level, completion overlay or restart target alike): every record whose `ownerId` is not the new id is released (`release()` is idempotent; `preparing` records are marked stale so their late result is released on arrival). The new owner's level and attempt are **parsed from its authored mount key** (`game.scenes[0].key`, e.g. `level-1-attempt-3`; the completion overlay's key is `complete`), never from `game.state`, because a death committed in a later tick of the same frame can already have advanced state. Candidates are then prepared: for a level owner `respawn` → `level-${L}-attempt-${a+1}`, `next` → `level-${L+1}-attempt-0` or `complete` when `L+1 === 2`; for the completion overlay `restart` → `level-0-attempt-0`.
    - **Invariant: at most one `preparing`-or-`ready` record per (owner, purpose).** `pause` is prepared for a level owner whenever that invariant allows it — so a consumed pause record (detected by its `consumed` status after the scene took the handle) triggers exactly one replacement preparation on the next reconcile, and repeated reconciles while a preparation is pending start nothing.
    - Scenes obtain candidates through options callbacks (`options.respawn()`, `options.next()`, `options.restart()`, `options.pause()`) that return the ready handle and mark the record `consumed`, or `undefined` when none is ready.
    - A rejected preparation marks the record `failed` and is retried on the next reconcile at most once (`retries ≤ 1`); a second failure surfaces the error panel and leaves the record `failed` (no further attempts).
    - `dispose()` releases every record; `stop()` (not used by this host) would drop all records because the contract invalidates unused candidates.
10. **Transition authority (level scene, one system).** `run.phase ∈ playing | dying | exiting | transitioning`. It reads `run.contacts` (facts written by system 4) and `run.pauseRequested` (latched by system 1), then clears `run.contacts`. Priority in `playing`: fatal > exit > checkpoint > pause. Rules:
    - `playing` + fatal → `dying`, `deathTimer = 30`, dispatch `died` **once**, clear `pauseRequested`; a checkpoint touched on the same tick is **not** committed. The death sound plays here.
    - `playing` + exit (no fatal) → `exiting`, clear `pauseRequested`; a checkpoint on the same tick is ignored.
    - `playing` + checkpoint `k` (no fatal/exit) → dispatch `checkpoint k` only if `k > run.checkpoint`, then `run.checkpoint = k`.
    - `playing` + `pauseRequested` → if `options.pause()` yields a handle, `scenes.push(handle)` and clear the latch; otherwise **the latch is retained** and retried next tick, so an edge that arrives during pause-candidate replenishment is not lost.
    - `dying` → when `deathTimer` reaches 0 **and** `options.respawn()` yields a handle → `scenes.set(handle)`, phase `transitioning`. While waiting the player is hidden and frozen in place; patrols keep moving.
    - `exiting` → when `options.next()` yields a handle → dispatch `exit` **once** in that same tick and `scenes.set(handle)`, phase `transitioning`. Durable command and stack command always travel together; the replacement's setup sees the advanced `level`.
    - `transitioning` is terminal for the instance: no further dispatch or stack commands. If the mount failed, the engine reports it through `diagnostic`; the host shows the error panel (Starfall pattern) with a reload action. This is the honest recovery on the current engine and is recorded as NGNE-7 friction.
    - The remounted level reads `state.read()` in setup, spawns the player at `checkpoint === 0 ? start : checkpoints[checkpoint-1]`, rebuilds all entities (patrols reset — accepted, documented) and positions the camera (step 5).
11. **Pause.** `overlay("pause", options)` with `blocksUpdateBelow: true`. Pushed only by the level scene (step 10). Popped only by the overlay's own system on the key edge **or** the host `resume` intent flag; the flag is cleared when read, so one commit sees at most one `pop`. **The host never calls `game.push/pop/set` directly**; DOM Pause/Resume buttons and `visibilitychange` (hidden → pause) set intent flags in `transitions.ts`. Overlay render reports `paused` through `onView` for the HUD.
12. Level content: level 1 teaches run / jump / gap / checkpoint / exit on a ~100-tile scroll; level 2 (~140 tiles) adds spikes, patrol enemies (walk, turn at walls and ledge edges, lethal on any contact — no stomping) and one-way platforms. Both 17 tiles tall; viewport shows 30×17 tiles.
13. Completion overlay (`overlay("complete")`, mounted with `set`, so it is the only scene): shows deaths and runs. Its single system follows the same authority rule with phases `idle | restarting | transitioning`: `Enter`/button latches `restarting`; each tick in `restarting` it asks `options.restart()`; when a handle arrives it dispatches `restart` **once** and `scenes.set(handle)` in that tick, then enters `transitioning` (terminal; a mount failure is surfaced by the host as in step 10). Repeated edges while waiting change nothing.
14. Minimal synthesized audio via `app.audio.scene("platformer")` for jump / checkpoint / death; scope disposed with `scene.defer`. Muted until the Start gesture unlocks audio (Starfall pattern).
15. Commits per coherent step: `[NGNE-15] Add level progression and death re-entry`, `[NGNE-15] Add pause overlay and second level`.

### Phase 3 — Findings record and engine-defect policy — Jira required work #4

### Phase 4 — Deterministic tests — Jira validation

18. `tests/platformer.test.ts` (discovered by `npm test`). A test harness `createHarness(fixtureLevels, script)` builds a headless `Game` and a `transitions.ts` registry and models the **`BrowserGame` frame order exactly**: `frame(ticks = 1)` runs `ticks` synchronous `game.tick(input, display)` calls from a **schedule keyed by tick** of `InputSnapshot`s (frozen objects built in the test) and host intents, then `game.render(frame, alpha)`, then `registry.reconcile(game)` (the `afterFrame` position), then one microtask drain. A preparation started in reconcile is therefore ready before the next frame's first tick, and a handle can only be consumed by a tick, so **activation is asserted on the first tick of the following frame**. Candidate delivery can additionally be **held back** by the test (a gate in the registry's prepare wrapper) to model slow preparation; the gate is released at a named frame and the assertion names the exact tick. Fixture levels are small string arrays defined in the test.
    - **Collision**: no tunnelling at max fall speed; landing sets `grounded`; ceiling contact zeroes upward velocity; one-way platform passes from below and lands from above; side bounds act as walls; fall-out line reports `fell`.
    - **Controller**: coyote window allows a jump N ticks after leaving a ledge and denies at N+1; jump buffer fires on landing within the window and expires after it; jump cut reduces apex height.
    - **Patrol**: turns at wall and at ledge edge; contact kills.
    - **Determinism A (pure input)**: two Games, same scripted inputs on fixture level, 600 synchronous ticks → identical `enumerate()`.
    - **Determinism B (host-driven)**: two harnesses with identical schedules through checkpoint, death, respawn, exit, pause/resume and restart → identical `enumerate()` at every tick.
    - **Progression**: checkpoint advances `checkpoint`; a lower checkpoint touched later does not regress it; checkpoint and fatal contact on the same tick → death wins and the checkpoint is not committed; death before any checkpoint respawns at start; `died` dispatched exactly once per death; respawn waits for the timer even if the candidate is ready; **late candidate**: respawn handle gated until frame F after the timer → `set` is issued on the first tick of frame F+1 and not before; **mount then die in one frame**: a 5-tick frame in which attempt `a` mounts on tick 1 and dies on tick 3 → reconcile derives the owner as attempt `a` from its key and prepares respawn `attempt-${a+1}`, even though `game.state.attempt` already reads `a+1`; remounted scene entity count equals a fresh mount and the player sits on the checkpoint tile; exit dispatches `exit` once and the replacement setup sees `level+1`; finishing level 2 mounts the completion overlay; restart with a pending candidate waits, dispatches `restart` once and mounts level 0; repeated restart edges while waiting do not re-dispatch.
    - **First frame**: render immediately after mount at alpha 0 and 1 → player visible within the viewport and camera clamped.
    - **Pause**: push overlay; N ticks later lower-scene stored poses are unchanged and its `Frame` output equals alpha-1 rendering; on the pop frame it still renders at alpha 1; after one gameplay tick it interpolates normally; a jump `released` edge consumed while paused still cuts the jump on resume.
    - **Candidate registry**: every record reaches `consumed`, `released` or a terminal `failed`; a stale-owner late result is released on arrival; **replacement by the completion overlay releases the last level's respawn/next/pause records before restart**; after restart, records from the earlier `level-0-attempt-0` instance are not confused with the new instance of the same key (different instance id); pause candidate is re-prepared exactly once after use; **repeated reconciles while a gated pause preparation is pending start no additional preparation** (count of `prepare` calls asserted); a rejected preparation retries once and then stays `failed` with the error surfaced; `dispose()` releases everything.
    - **Transition authority**: pause intent during `dying`/`exiting` is cleared and ignored; a pause edge arriving while no pause candidate is ready is retained and honoured when one arrives; fatal and exit contact on the same tick → death wins; DOM resume flag and key edge on the same tick → one `pop`; player physics does not run while `dying`.

## Risks / open questions

- **Mount failure after `exit`**: state is ahead of the stack; the instance is `transitioning` and inert; the host shows the error panel. Acceptable for an example; the semantics are already in the architecture and get an explicit test plus a FINDINGS entry for NGNE-7.
- **Preparation failure**: asset-free scenes only fail on lifecycle misuse; still, the registry retries once and then surfaces the error.
- **`stop()` invalidation**: the host never calls `app.stop()`; tab hide uses the pause intent. If a future host does stop, the contract already says unused candidates are invalidated — the registry must drop its records on stop (test it).
- **Pause candidate replenishment gap**: after a pause/resume the next pause request may arrive before the new candidate is ready; the latch (step 10) covers it and a test asserts the pause happens on the first frame a handle exists.
- **Frame-boundary coupling**: the registry reconciles once per host frame from `afterFrame`, so a transition can never be observed by the host mid-frame and a candidate can never be consumed in the frame that prepared it; the harness reproduces this ordering exactly (ticks → render → reconcile → drain), which is why it models frames rather than ticks and asserts activation on the following frame's first tick.
- **Same-tick key edges**: the level pushes pause at tick T; the overlay mounts at commit and blocks lower updates from T+1, so one edge cannot both push and pop.
- **Patrol determinism**: no RNG needed; if randomness is added it goes through `scene.random`.
- **Unknown until built**: whether any engine defect reproduces. Budget for at most one small in-place fix; anything larger is filed.
